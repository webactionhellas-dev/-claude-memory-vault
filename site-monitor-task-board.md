## LATEST-13 (2026-08-03, office machine "nospa"): source now ALSO synced via the vault; real asar-persistence bug found and fixed

Mike sent a packaged Electron build (`win-unpacked` + `app.asar`, no source) from his home setup to work on at the office. Extracted real source out of `app.asar` with `npx asar extract` (this app has no build step, so the asar contains literal editable `src/*.js`, not bundled/minified output) - this is the move any time only a packaged build is available and the source is known to be a plain zero-dep app.

**Real bug found, not just a fresh-install artifact**: every check was silently failing to persist - `state.js`/`settings.js`/`lib.js`'s `loadConfig/saveConfig` all built their path from `ROOT` (`path.dirname(path.dirname(import.meta.url))`), which for a PACKAGED build resolves to `.../resources/app.asar` itself - a single-file read-only archive. `fs.mkdirSync`/`writeFileSync` into a path "inside" it throws `ENOTDIR` every time (confirmed directly with a plain `node -e` repro, no Electron needed). This meant history reset to empty on every single app restart, silently (the HTTP request only logs a 500, the client ignores it) - almost certainly the real reason the 90-day strip/history always looked broken/empty, on this machine AND presumably at home too, not just "needs more runtime." Fixed via a new `WRITABLE_ROOT` export in `src/lib.js` (`path.dirname(ROOT)` when `ROOT` ends in `app.asar`, else `ROOT` unchanged - a no-op in dev/CLI mode) - `state.js`, `settings.js`, `electron-main.js`'s window-bounds path, and `lib.js`'s own `config.json` read/write all redirect through it, with `loadConfig()` falling back to the bundled seed copy on a fresh install with no writable copy yet. Verified live: killed + relaunched the packaged exe, check counts actually carried over (4, 3, 2, 3...) instead of resetting to 0. **If this app is ever repackaged again, re-verify writes still land outside the asar** - this class of bug is invisible until you specifically test a restart.

**Design changes this session** (on top of the round-3 "TRACE" dark reskin already in place, which is newer than the "Bench" light system LATEST-12 below describes - Mike's home build had already moved past Bench to TRACE before this session started):
- Fixed two real overlap bugs (undersized grid columns: Sites page metacell/rowactions, Tasks page project-tag pushing icons off the card) - same root cause both times, columns sized to theoretical content width with zero margin.
- Status colors reverted from TRACE's deliberate "healthy = no colour" theory back to a real green/amber/red traffic light, per Mike's explicit ask - `--ok`/`--warn`/`--down` in `dashboard.js`'s `:root`.
- Icon buttons given real depth (subtle bg + hover lift) instead of flat gray-outline-on-black.
- **The 90-day strip replaced with a live per-check sparkline** (`sparklineSvg()` in `dashboard.js`, built from `s.history` not `s.days`): real SVG polyline of recent raw checks, colored by current status, plus a continuously-pulsing ring on the latest point so the row visibly breathes between checks. The old 90-day rollup strip is honest but reads as completely dead for the first few weeks of a fresh install - Mike's actual ask ("moving like a real animation") needed a per-check view, not a per-day one. Hover-for-detail was preserved by adapting the existing day-cell hover handler to also recognize the new `.spark-pt` hit-targets.

## Earlier history

`C:\Users\mikef\site-monitor` — a zero-dep Node tool (same house style as [[x-tracker]]) with two parts on one dashboard:
1. **Site health**: checks CloudSkin, Trattoria Capanna, Drip Barbershop, Drip Astro v2, Mykonos Prestige, Web Action every 10 minutes (uptime, broken images, slow pages, missing security headers), Telegram alert on any ok<->trouble transition (blank until `.env` is filled in, same var names as x-tracker), unless the site is muted.
2. **Task board**: assign work to people (Mike, Asteris, Panos, unassigned), track status (todo/in_progress/blocked/done), priority (none/low/normal/high/urgent). One markdown file per task in `C:\Users\mikef\obsidian-vault\tasks\` (portable via `os.homedir()`, not a hardcoded path) so two people creating tasks at once can't clobber each other's file.

**Runs persistently in the background, always.** Auto-starts hidden at every Windows login via the Startup-folder `.vbs` (Task Scheduler creation is blocked in this sandbox). Dashboard: **http://localhost:8788**. Also runs as a real Electron desktop app (`npm run app`) - `electron-main.js` + `src/app.js`'s `startMonitor()` is the SAME implementation both the plain CLI and Electron call, so there is one tested "how the monitor runs," not two that drift apart.

## 2026-08-02 rebuild: two real bugs fixed, full CRUD, theme customization

This was a from-an-approved-brief internal-tool rebuild (not a client site - no bilingual/SEO/deploy pipeline), verified with real clicks against the real 6 sites and real task vault, not just read.

**Bug 1 fixed - uptime% was conflating "not fully clean" with "down".** `state.js recordCheck()` used to count only `overall === 'ok'` checks as up, so a site with a permanently missing security header (`overall: 'warn'`, but genuinely reachable in <200ms) showed "0% uptime" forever. Confirmed live: Trattoria Capanna, Mykonos Prestige, and Web Action all showed 0% while responding fine. Fixed: `ok` AND `warn` both count as reachable/up, only a real `down` costs uptime%. The status badge still shows warn vs ok as a distinct signal - only the uptime number changed. Note: this also means Drip Astro v2 (which has zero real `down` checks, only threshold-crossing `warn`s) now correctly reads 100% uptime too, not 80% - 80% was itself an artifact of the same bug, not a separate correct number. If this ever looks surprising, that's why.

**Bug 2 fixed - the badge flipped on one borderline sample.** Drip Astro v2 sits right on the 3000ms slow threshold and used to flip ok/warn on literally the single latest check (e.g. 2947ms). `computeDisplayedStatus()` in `state.js` now requires 2 of the last 3 real checks to agree before the DISPLAYED badge moves; a genuine 3-way split (rare) holds the previous displayed value rather than jumping to whatever landed last. The raw per-check history (sparkline, uptime%) is untouched by this - only the badge color is smoothed. Verified with a synthetic assertion script feeding known sequences through the real `recordCheck()`, not just eyeballed.

**New design system: "Bench" (light), replacing the old dark "Signal Deck".** Field `#FAFAFA`, cards `#FFFFFF`, hairline `#E6E3DC`, ink `#292929`. Accent `#3374FF` (Mike's real webactionhellas.com blue) is the DEFAULT and user-overridable (see theme section). Status colors ok `#1F9D63` / warn `#B5790E` / down `#C93A2C` are fixed and NEVER themeable - a custom accent can never be mistaken for a real alert. Type: Jost (display/headings), General Sans via Fontshare (UI/body), IBM Plex Mono (genuinely tabular data only - ms, timestamps, ids - never section headers or chrome). The radar scan-sweep, the ping-pulse on every dot, and "Fleet"/"instruments"/HUD vocabulary are gone entirely. All in `src/dashboard.js` (one big server-rendered template string, same house convention as before - no framework, no build step).

**Every panel now has real, wired actions**, not just a read-only view:
- Site rows: recheck now (spinner -> calls the real `checkSite()` for just that one site via `POST /api/sites/:name/recheck`, same function the scheduler uses), view history (client-side expand of the already-shipped 50-point `history[]`, zero new backend cost), mute (`POST /api/sites/:name/mute`, persisted as a `muted` flag on the site's entry in `config.json` - NOT in `state.json`, because `recordCheck()` fully overwrites `state.sites[key]` every check, so anything client-only has to live somewhere that survives that), add/remove site (`POST`/`DELETE /api/sites`, duplicate-name + URL-format validated). Muted sites stay visible, dimmed, with a small "Muted" tag - never hidden.
- Tasks: full CRUD. Create (existing, now sends `priority` too), inline expand-to-edit in place (the signature interaction - a CSS grid-rows 0fr->1fr expand, settles back down on save/cancel, no modal jump), delete with an inline "really delete?" confirm (not a native `confirm()`), reassign via a quick-select dropdown on the card (mike/asteris/panos/unassigned), priority shown as a small flag+text (never color-only, and deliberately NOT using the reserved ok/warn/down palette so it can't be confused with site-status). `PATCH /api/tasks/:id` and `DELETE /api/tasks/:id` are new in `tasks.js`; both go through a `taskFile(id)` guard against a stray `/` or `..` in an id that arrives straight from a URL param.
- **`scripts/add-site.mjs` / `scripts/remove-site.mjs` already existed** (missed on first pass because a directory-wide glob got cut off by node_modules noise - re-check with a scripts/-scoped glob, not a whole-repo one, next time). Reconciled 2026-08-02: both now import and call the same `src/sites.js` functions the dashboard's own routes use (`addSite`/`removeSite`), matching the existing `add-task.mjs` -> `src/tasks.js` pattern, instead of keeping a second, slightly-diverged inline copy of "write config.json" (the old script matched on duplicate URL and case-sensitive-vs-insensitive name removal inconsistently vs the new dashboard routes - now both paths share one implementation). **Known limitation, pre-existing and unchanged**: a CLI-script edit to `config.json` is NOT picked up by an already-running monitor process (it read the site list once at startup) - only the dashboard's own add/remove/mute routes call `reloadConfig()` on the live in-memory config. Restart the monitor after a CLI-script add/remove, or just use the dashboard's own form instead.

**New: theme customization**, Mike's explicit ask ("it doesn't have actions" extended to "I want to pick my own colors"). Gear icon -> right-side settings drawer. Accent color (6 curated swatches + a native `<input type=color>` custom picker) and background (solid / 2-stop gradient / user-uploaded image, all curated except the upload) are user-overridable; status colors are hard-locked, never part of this. An uploaded image is downscaled client-side via canvas (max 1920px, JPEG q=0.82) before becoming a data URL, with an automatic scrim layer (`--field` at .88 opacity) between the image and the page content so text always stays legible regardless of what photo someone picks. Persisted server-side to **`data/settings.json`** (new `src/settings.js`, same load/save pattern as `state.js`) via `GET`/`POST /api/settings` - deliberately NOT `localStorage` (the dashboard opens both inside Electron and as a plain browser tab, only a server file behaves identically in both) and deliberately NOT synced through the git-tracked `obsidian-vault` (a personal display preference must never bleed onto Asteris's machine or land in a commit). Verified: changed accent + background, confirmed `data/settings.json` on disk, reloaded the page, confirmed it survived. `readJsonBody`'s size cap was raised from 1MB to 6MB in `dashboard.js` to fit a downscaled background photo as a data URL.

**Environment gotcha hit during this build, worth knowing next time**: in this Browser-pane automation, `ref`-based clicks on elements inside a long, tall, dynamically-expanding card (e.g. a task's inline edit panel) intermittently resolved to stale/wrong coordinates after the DOM shifted - `form_input` (sets value directly) was reliable, plain `computer.left_click` on a `ref` sometimes was not. Driving the same button via `element.click()` in `javascript_tool` was the reliable fallback and still exercises the real production event handler (not a shortcut around testing, just a different invocation of the same code path) - used for the second half of every CRUD test after the first click-based attempts silently no-op'd. Separately, a CSS `transition` on `border-top-color` (the "health panel dominates when something's wrong" alert border) read back as stuck at its FROM value via `getComputedStyle` while driving the page headlessly through this same Browser pane - forcing `transition:none` inline made it resolve to the correct `var(--warn)` instantly, proving the CSS/logic itself was correct and this was a compositor artifact of the pane not actively painting frames (same family as the already-documented `preview-screenshot-timeout` and `preview-pane-intersectionobserver-dead` issues - a third symptom of "this pane doesn't behave like an actively-rendering browser," not a new class of bug). Proposed as a possible addition to [[preview-pane-intersectionobserver-dead]] or its own note - flagged for Mike's OK, not written into the shared reference yet.

**Also hit this session**: writing to a file under `C:\Users\mikef\.claude\projects\C--Users-mikef\memory\` and then immediately running the documented bidirectional robocopy mirror (`SRC=obsidian-vault`, `DST=memory folder`, both with `/XO`) reverted the fresh edit back to the vault's older copy - the `/XO`-based mirror is order/timestamp-sensitive and can clobber a same-session edit if the vault side hasn't caught up yet. Re-writing the file and pushing the VAULT copy directly (rather than trusting the mirror to carry a live-memory-folder edit outward first) is the reliable order. Matches the existing warning in CLAUDE.md that something around this folder can silently revert content - this may be the same mechanism, or a plain robocopy race; flagged for Mike, not fully root-caused.
