## ROOT CAUSE FOUND AND FIXED (later same evening, 2026-08-07)
Deployed a read-only diagnostic (`temp-webhook-secret-audit-20260807`) instead of guessing: `STRIPE_WEBHOOK_SECRET` exists in BOTH `Deno.env` (a Supabase Edge Function secret) AND `app_secrets` (a DB row), the two hold DIFFERENT values, and `env.ts`'s `getSecret()` always prefers `Deno.env` when present. **Nobody on this project has reliably had Supabase Dashboard/CLI access to update Deno.env**, so every "fix" (2026-08-06's rotation included) only ever updated `app_secrets` — which was never actually being read. Deno.env silently kept winning with a stale value, forever, invisibly. Not a one-off bad secret: a structural dual-source-of-truth bug that will keep recurring on ANY future rotation unless closed.

**Fix shipped (no new Stripe endpoint needed — the app_secrets value, written during the Aug 6 fix, turned out already correct, just never read):**
1. `stripe-webhook/index.ts`: added `resolveWebhookSecret()` — for this ONE key, prefer `app_secrets`, fall back to `Deno.env` only if the DB row is empty, `console.error` loudly if both are set and disagree. Deliberately scoped to this one call site, not a global `getSecret()` change (blast-radius discipline).
2. Verified END-TO-END before trusting it: deployed a second temp function (`temp-webhook-live-selftest-20260807`) that reads the real `app_secrets` secret server-side, builds a genuine HMAC-SHA256 Stripe-signed request (an inert `account.updated` event type stripe-webhook doesn't handle — zero side effects even on success), and POSTs it to the LIVE redeployed function. Result: **200, "signature valid"**. Confirmed via `get_logs` immediately after: every real `stripe-webhook` call since the redeploy is 200; the last 400 is timestamped BEFORE the redeploy. Manually re-triggered the reconciler right after: 10 orders checked, 0 needed healing.
3. `stripe-pending-reconciler`: added `checkSecretDrift()` — every 15-min cycle now also checks `STRIPE_WEBHOOK_SECRET`, `STRIPE_SECRET_KEY`, and `STRIPE_PUBLISHABLE_KEY` for exactly this env-vs-db disagreement and emails an immediate, specific alert if any exist, instead of Mike having to notice a pattern of vague "order(s) auto-fixed" emails and ask why again. **First real run of this check already found a SECOND live drift on `STRIPE_PUBLISHABLE_KEY`** (matches the known 2026-08-06 incident in `_shared/stripe.ts` — that one has its own self-correcting fallback in `resolvePublishableKey()` already, so lower risk, but the underlying env/db disagreement is still sitting there unresolved and now alerting). Mike will get an "ALERT: 2 secret(s) drifted" email from tonight's manual test trigger — expected, not a new problem.
4. Committed + pushed to git (`webactionhellas-dev/cloudskin-v67`, picked up by the home auto-sync as commit `3805c54`) — the fix lives in source, not just live-patched, so it survives the next `deploy.mjs` run.

**Left for a future session, not urgent:** the stale Deno.env value is now harmless (code no longer reads it first for this key) but still sitting there — worth clearing via the Supabase Dashboard eventually for hygiene. `STRIPE_PUBLISHABLE_KEY`'s env/db disagreement (surfaced by the new check, not fixed tonight — out of scope, already self-correcting, revisit if it ever actually breaks the embedded Payment Element again).
