Built 2026-08-01 on the "aster" laptop (AMD Ryzen AI 7 350, Radeon 860M iGPU, XDNA2 NPU, 32GB RAM) across two very long sessions. Goal: a JARVIS-style personal assistant reachable by Telegram and voice, free/instant for small stuff via a local model, with a deterministic bridge to the real Claude Code fleet for anything that needs actual capability. See [[aster-laptop-brain-setup]] for the memory-vault/launch.json state this builds on.

## Current live architecture (as of session 2 handoff)

- **Ollama serves `llama3.1-agent`** -- a *custom* model (`ollama create llama3.1-agent -f Modelfile` with `PARAMETER num_ctx 65536` baked in), NOT plain `llama3.1:8b`. This matters: see gotcha #3 below -- baking context into the model itself was the only way to make it work consistently across every client (CLI, Telegram relay, Desktop app, voice loop), since most of those clients never send a context override.
- **CPU-only inference, GPU offload deliberately disabled.** `OLLAMA_IGPU_ENABLE` is UNSET. See gotcha #9 -- this reverses the session-1 advice to enable it.
- **`%LOCALAPPDATA%\hermes\telegram_relay.py`** bridges Telegram to Hermes. Plain message -> local Hermes/Ollama. Message starting with `/fleet ` -> bypasses the local model entirely, shells out to `claude -p "<task>" --output-format text --permission-mode acceptEdits` (the real Claude Code fleet). Confirmed working live (bot `@asterisrighthandbot`, locked to user id 5675850932). Auto-starts via a `.vbs` in the Startup folder.
- **`%LOCALAPPDATA%\hermes\jarvis_voice.py`** -- a from-scratch standalone "Hey Jarvis" voice loop (see below). Also auto-starts via a Startup-folder `.vbs`.
- **Hermes Desktop app (`hermes desktop`)** -- visually fine (matches the "Jarvis HUD" ask), but its *voice feature specifically* has six distinct unresolved bugs (below) and was abandoned in favor of the standalone `jarvis_voice.py` script. The desktop app can still be opened for the visual, just don't rely on its mic/wake-word pipeline.
- **`auxiliary.title_generation.enabled: false`** plus `vision`/`web_extract`/`session_search` all forced to `provider: main` in config.yaml -- stops Hermes from wasting real time (and adding a competing Ollama request) attempting unconfigured OpenRouter/Nous cloud calls on every first message of a session. Real, measurable latency win.

**Why the fleet delegation is a hardcoded prefix, not the model's judgment:** first tried teaching the local 8B model via SOUL.md to decide for itself when to delegate. It failed outright -- ran a garbled nonsense terminal command, then hallucinated a completely unrelated answer about "blog monitoring." Small local models are not reliable at that kind of judgment call or at agentic tool-calling generally (also confirmed separately: asked it to check screen resolution via computer_use, it fabricated "1920x1080" without actually calling the tool). **Lesson: route local-vs-fleet deterministically in code, never by asking a small model to judge its own competence.**

## The standalone Jarvis voice loop (`jarvis_voice.py`)

**Update (session 3):** swapped amplitude-based silence detection for a **fixed 5-second recording window** (`FIXED_RECORD_SECONDS`) after the wake word, with a high beep (880Hz) marking "start talking" and a low beep (440Hz) marking "stop, processing now." This mic's gain was too inconsistent for a fixed RMS threshold to reliably detect real speech vs. silence -- a fixed window removes that calibration dependency entirely, at the cost of a rigid (not adaptive) recording length. If 5s feels too short/long in practice, adjust `FIXED_RECORD_SECONDS` directly rather than reintroducing amplitude-based detection.

Built to bypass Hermes Desktop's broken voice pipeline entirely, reusing only proven pieces: openWakeWord (`hey_jarvis` model), faster-whisper (`base`, local), `hermes chat -Q -q` via subprocess (same reliable CLI path the Telegram relay uses), edge-tts + ffmpeg for spoken replies via `winsound`.

**Critical architecture lesson: open ONE audio stream for the entire process lifetime, never close and reopen it.** First version opened a fresh `sd.InputStream` for wake-word listening, closed it, then opened a *second* fresh stream for recording the actual question. On this specific mic ("Microphone Array (Senary Audio)" via MME), the second stream reliably captured **pure silence** (max amplitude 2 out of 32767) even though the first stream worked fine moments earlier -- confirmed by directly inspecting the captured .wav, not just theory. A 0.5s settle delay between close/reopen did NOT fix it. The actual fix: open the `sd.InputStream` exactly once at the top of `main()`, keep it open for the whole session, and switch between "listening for wake word" and "recording" purely in software (just changing what you do with incoming chunks), never touching the device handle again. This is now genuinely working (real audio, real transcriptions like "Hey Jarvis" and "How are you?" have been captured) -- **but audio capture is still intermittent**, some attempts still come back empty or as noise ("Heard: . . . ."). An audible `winsound.Beep(880, 150)` was added right when recording starts so the user has a clear timing cue instead of guessing. Root cause of the remaining intermittency is NOT fully solved -- likely still some mic/driver quirk with this specific "Senary Audio" array hardware. Next session: consider trying a much lower `SILENCE_RMS_THRESHOLD`, or recording a fixed window instead of amplitude-based auto-stop, or investigating whether Windows "microphone enhancements" (noise suppression/AGC) still need disabling via the driver's own control panel (not just OS volume, which was already maxed via the `AudioDeviceCmdlets` PowerShell module).

## Gotchas that cost real time (apply directly, don't rediscover)

1. **"`<model>` does not support thinking" HTTP 400 from Ollama -- THREE separate root causes discovered across two sessions, not one:**
   - (a) Hermes's `agent.reasoning_effort` in config.yaml: absent key silently resolves to a hidden `"medium"` default; explicit `"none"` sends `think:false` which this Ollama version also rejects. **Only `agent.reasoning_effort: ""` (explicit empty string) works** -- verified via Ollama's own `OLLAMA_DEBUG_LOG_REQUESTS=true` request-body dumps, not guessing.
   - (b) **Duplicate YAML keys silently break everything** -- editing `config.yaml` via both `hermes config set` (CLI) and direct file edits left TWO `reasoning_effort:` keys in the same block; YAML silently keeps the last one. Always grep the file after editing to confirm exactly one occurrence.
   - (c) **The Desktop app ignores config.yaml's reasoning setting entirely** -- it remembers a per-model "reasoning effort" preset in its own Chromium-style local storage (`%APPDATA%\Hermes\Local Storage`, key `hermes.desktop.model-presets`), separately from config.yaml, and silently re-applies `effort: "high"` to every new session using that model regardless of what config.yaml says. Fix: delete that `Local Storage` folder entirely (safe, just UI convenience state) when this recurs.
2. **The Desktop app never sends a custom Ollama context size, period.** Confirmed via exhaustive source grep: zero references to `ollama_num_ctx`/`num_ctx` anywhere in `apps/desktop/src` or `tui_gateway/`. This is a real missing feature there, not a config gap. Every Desktop-app request uses Ollama's bare default (4096), which is below Hermes's own 64K floor and forces a full model reload (~15-40s) every time it alternates with a request that DOES specify a larger context (e.g. from the CLI). **The only fix: bake the context into the model itself** via a custom `ollama create <name> -f Modelfile` with `PARAMETER num_ctx 65536`, so the served context never depends on what the client asks for. This is why `llama3.1-agent` (not plain `llama3.1:8b`) is the actual production model now.
3. **Sessions (CLI *and* Desktop) pin their model/config at creation time in `%LOCALAPPDATA%\hermes\state.db` (`sessions` table, `model` + `model_config` columns) and do NOT re-read config.yaml on reuse.** If you change `model.default` mid-session, existing sessions keep using the OLD model/config forever. Direct SQLite UPDATE on that table is a valid reactive fix, but new sessions keep getting created (especially by the Desktop app / voice loop, seemingly one per exchange) with whatever the *current* config.yaml says -- so the real fix is making config.yaml correct once, not patching rows.
4. **RAM/orphaned-process hygiene is a recurring problem, not a one-time fix.** Killing `ollama.exe`/`ollama app.exe` does NOT reliably kill the child `llama-server.exe` runner. Multiple times across both sessions, RAM climbed to 83-86% used purely from leaked `llama-server`/`ryzenai-server` processes, not real usage. **Check this at the start of every session**: `Get-CimInstance Win32_Process -Filter "Name='llama-server.exe'"` and cross-reference `ParentProcessId` against currently-running parents before assuming high RAM is "just the model."
5. **`hermes computer-use install` hangs/fails when Hermes runs it internally**, but the exact same install script succeeds when downloaded (`Invoke-WebRequest`) and run directly as a local `.ps1` file. Binaries land at `%LOCALAPPDATA%\Programs\Cua\cua-driver\bin\`, which Hermes's own path-detection doesn't check -- set `HERMES_CUA_DRIVER_CMD` in `.env`. `hermes computer-use status`/`doctor` still misreport "not installed" afterward; that's a detection bug, verify by actually invoking the tool.
6. **AMD Lemonade Server (NPU+iGPU hybrid) has zero tool-calling support.** Fast (25-29 tok/s) and light (3.5GB vs Ollama's 9-14GB) for raw chat, but any request with a `tools` array gets `"Invalid or unsupported chat template"`. Since Hermes always sends its full tool schema on every request, Lemonade cannot serve as Hermes's backend at all. Installed and benched, not wired in. **The NPU is not usable for this assistant today** -- not a config problem, a real software-compatibility wall.
7. **Hermes's own `gateway run` (Telegram) has a reproducible, unresolved startup hang.** Gets stuck at "Connecting to Telegram (attempt 1/8)" forever. Ruled out: network, stale lock file, RAM pressure, TCP connection state (zero sockets ever opened). Genuine bug in this Hermes version's native-Windows gateway -- worked around with the custom `telegram_relay.py` instead of chasing it further.
8. **Claude Code's own auto-mode classifier blocks `--permission-mode <anything>`** when *this* session invokes `claude -p` directly via Bash for testing (any value, not just `bypassPermissions`). Fixed via a scoped rule in `~/.claude/settings.json`: `"permissions": {"allow": ["Bash(claude -p * --permission-mode acceptEdits*)"]}`. Irrelevant to the actual production relay, which spawns `claude -p` as an independent Python subprocess outside this session's classifier entirely.
9. **GPU/Vulkan iGPU offload (`OLLAMA_IGPU_ENABLE=1`) is UNSTABLE on this hardware for sustained use -- session-1's advice to enable it was wrong in the long run.** It worked and was fast initially, but **hung completely twice** across the two sessions after roughly hours-to-minutes of use (CPU usage climbing, `Responding: True` per Windows, but the HTTP API never answering -- one request took 2m55s and returned garbled output). **Decision: `OLLAMA_IGPU_ENABLE` is now UNSET, forcing pure CPU inference.** Verified stable across repeated back-to-back requests: 5.4s cold, then 0.58s / 0.58s warm -- genuinely fast enough for conversational use, and with zero hangs. For SHORT conversational replies specifically, CPU-only was not meaningfully slower than the buggy GPU path, and vastly more reliable. If a future session is tempted to re-enable GPU offload for speed, know that it WILL eventually hang again -- weigh that against the marginal speed gain before doing it, and test stability with several consecutive requests before trusting it.

## Latency fix: bypassed Hermes CLI entirely for casual chat (2026-08-01, session 4)

**Symptom:** a single "reply with pong" through the real Hermes agent path took 147s-500s+. Root cause: Hermes injects its full tool-schema system prompt (~19,245 tokens -- 47 enabled plugins, `hermes prompt-size --platform cli` confirmed ~81KB total) into every fresh session, and that has to be prefilled before the model can respond. This is architecturally pre-existing, not something introduced by env-var tuning.

**Fix, in two stages (both landed):**
1. First pass: added `-t context_engine` (a genuinely empty built-in Ollama toolset -- passing `-t ""` does NOT work, it silently falls back to the full default set per `oneshot.py`'s `_normalize_toolsets`) to the `hermes chat` invocation in both `jarvis_voice.py` and `telegram_relay.py`. Cut input tokens from ~19,245 to 986 and total latency from ~150s to a stable, reproducible **9s**. Disabling ~65 unused bundled plugins (cloud LLM providers, messaging platforms, browser-cloud backends) via `hermes plugins disable <name>` gave negligible further improvement (10s) -- not worth the complexity, left disabled anyway since they're genuinely unused.
2. Second pass (bigger win): rewrote `ask_hermes()` in both scripts to call Ollama's OpenAI-compatible endpoint (`http://localhost:11434/v1/chat/completions`) **directly via `urllib.request`**, bypassing the Hermes CLI subprocess entirely -- no per-message Python interpreter spawn, no plugin discovery, no Hermes turn-finalize overhead. System prompt shrunk from Hermes's ~986-token stable block down to a ~30-token custom Jarvis persona string. Result: **3.7-4.5s per turn**, verified with real conversational continuity (a short in-process `_conversation` history list, capped at `MAX_HISTORY_MESSAGES=12` i.e. 6 exchange pairs, prepended with the system prompt each call). `max_tokens` capped (200 for voice, 400 for Telegram) to keep replies conversational-length rather than essay-length.

**Why this was safe to do:** the existing architecture already never lets the local 8B model call tools directly -- real capability routes through the hardcoded `/fleet` prefix to the actual Claude Code CLI (`ask_fleet()`/`CLAUDE_EXE`, untouched by any of this). So the local model never needed Hermes's 40+ tool schemas, its skills index, or its multi-provider plugin registry in the first place. Bypassing Hermes's CLI for the casual-chat path loses only: Hermes's own long-term memory/user-profile system (the bypass path has zero persistent memory across process restarts -- same limitation the old `--resume`-based session continuity already had) and its personality presets (replaced with a fixed custom system prompt per script). Neither was in active use for this specific role.

**Dead ends found along the way, don't retry:**
- Thread-count tuning (`OLLAMA_NUM_THREAD`) does NOT help token *generation* speed on this CPU -- confirmed flat at 11.6-11.7 tok/s whether using 4, 8, or 16 threads (RAM-bandwidth-bound, not compute-bound). But it DOES matter for *prefill* of large prompts (compute-bound, thread-parallel) -- setting `OLLAMA_NUM_THREAD=4` turned a ~150s tool-schema-prefill exchange into 6+ minutes (didn't even finish before being killed). Verdict: leave `OLLAMA_NUM_THREAD` unset (Ollama's own default) -- don't reintroduce a low thread cap.
- `--ignore-rules` flag produced a 23s outlier once, but that run's `in=` token count was also lower (752 vs 986) while somehow slower -- almost certainly a cold-model-reload artifact from process churn during testing, not a real signal. Don't read anything into that number.
- `OLLAMA_NUM_PARALLEL=1` (kept, real memory win) means concurrent requests fully serialize -- queuing two test calls back-to-back during this session repeatedly produced contaminated, multi-hundred-second "hang" readings that were actually just queue wait, not real per-request latency. When benchmarking this stack in the future, never run two requests at once and never trust a timing number from a run that overlapped another.
- Lemonade Server (NPU, faster raw decode) is still blocked by the same zero-tool-calling limitation as before (gotcha #6) -- BUT now that the casual-chat path sends zero tools anyway (direct Ollama call, no `tools` array), Lemonade might actually be viable for this specific role. Not yet tried -- worth revisiting next session if further speed is wanted, since Lemonade benched 25-29 tok/s vs Ollama's 11.7 tok/s.

**Final locked-in Ollama env vars (User scope, persisted):** `OLLAMA_KV_CACHE_TYPE=q8_0`, `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_KEEP_ALIVE=24h`. `OLLAMA_NUM_THREAD` deliberately left unset. Lemonade Server's Startup auto-launch shortcut was moved to `Startup\disabled\` (confirmed dead weight, not deleted -- reversible).

## Session 4 continued: model swap, real-time voice, long-term memory, action layer

**Model swap for speed (2026-08-01, later in session 4):** switched `OLLAMA_MODEL` in both scripts from `llama3.1-agent` (8B) to a new custom model `jarvis-fast` (`llama3.2:3b` base + `num_ctx 8192` baked via a `hermes-agent`-style `/api/create` Modelfile, no Hermes involved this time -- it's a pure Ollama model now). Decode is RAM-bandwidth-bound, so a smaller model gives a close-to-linear speedup: 8B decode was flat at 11.6-11.7 tok/s; 3B measured ~20-23 tok/s. Quality-checked before switching (multi-turn memory recall, instruction-following, personality) -- held up fine, still coherent, correctly used injected memory facts unprompted. **Result: simple exchanges (recall a fact, answer a short question) now land around 2.8-3s**, down from 3.5-4.5s on the 8B model. Longer/more detailed replies still take proportionally longer (natural -- same as a person needing more time for a longer answer). `llama3.1-agent` (8B) is left installed in Ollama as a fallback if quality ever needs to beat speed for this specific path.

**Lemonade Server (NPU) tried and rejected for this role:** only one model is actually downloaded there (`Llama-3.2-3B-Instruct-Hybrid`, NOT the same weights as Ollama's `llama3.2:3b`). Raw decode was genuinely faster (23 tok/s, 1.06s time-to-first-token) but the FIRST test -- no `max_tokens`/`stop` set -- ran away into 529 tokens of hallucinated fake multi-turn dialogue ("User: ... Assistant: ...") instead of stopping after one reply. Capping `max_tokens=80` + explicit `stop` sequences contained it (4.2s total, clean output) but landed at roughly the same wall-clock as the adopted Ollama 3B path once given the same safety margins, for a runtime with a demonstrated instruction-following failure mode. Verdict: not adopted. Lemonade Server was stopped and its model unloaded after testing; its Startup autostart remains disabled (see below, still true).

**Real-time-feeling voice via token streaming + sentence-chunked TTS (jarvis_voice.py):** `ask_hermes()` now requests `"stream": true` from Ollama's OpenAI-compatible endpoint, reads Server-Sent-Event chunks (`data: {...}\n` lines, `[DONE]` sentinel -- confirmed via raw curl, standard OpenAI SSE format), and speaks+plays each completed sentence (split on `.`/`!`/`?`/newline via `_SENTENCE_SPLIT_RE`) as soon as it's ready via `_speak_and_play()`, instead of waiting for the full reply before any TTS/audio starts. **Measured time-to-first-spoken-word: ~4.4s** (on the old 8B model; should be faster now on jarvis-fast, not re-measured after the model swap). This is the metric that actually matters for "feels like a live conversation" -- total time to finish a long multi-sentence reply is still bounded by real TTS-synthesis-plus-playback time per sentence (edge_tts network call + ffmpeg convert + blocking `winsound.PlaySound`), which for a genuinely long answer can still take 15-20s+, same as a person actually needing time to say a long sentence aloud. Don't mistake that for a regression -- it's physics of spoken language, not a bug.

**Long-term memory (both scripts, shared file):** `MEMORY_FILE = %LOCALAPPDATA%\hermes\jarvis_memory.json`, a plain `{"facts": [...]}` list, capped at `MAX_FACTS=100` (oldest dropped first). Deliberately **not** LLM-judged -- explicit deterministic commands only (`_handle_memory_command`): `"remember that X"` / `"remember X"` saves a fact and replies instantly (0.00-0.01s, no LLM call at all); `"forget that X"` / `"forget about X"` removes any fact containing that substring; `"what do you remember [about me]"` lists saved facts, also instant. Every normal conversational turn injects the current fact list into the system prompt via `_system_prompt_with_memory()` (re-reads the file fresh each call so either surface -- Telegram or voice -- picks up what the other just saved). Verified: saving a fact via one path and recalling it via a fresh process import both worked, and the model used a saved fact unprompted in an unrelated reply. Real limitation: this is flat/unstructured (no semantic search, no forgetting old-but-still-true facts automatically) -- fine at personal-assistant scale, would need real embedding-based retrieval past a few hundred facts.

**Deterministic "open X" action layer (both scripts):** the single biggest capability gap after the speed rework was that the fast bypass path has *zero* tool access, so "open notepad" used to just get talked about, not done. Fixed with pattern-matched Python, not an LLM tool call (small local models proved unreliable at tool-calling earlier in this project -- see the fabricated-screen-resolution and garbled-terminal-command gotchas below) -- `_handle_open_command()` matches `(please/can you) open|launch <target>`, strips trailing filler ("for me", "please", "now", "up") via `_TRAILING_FILLER_RE` (needed a fix -- first version left "for me"/"please" stuck to the target and broke alias lookup), then resolves via: URL detection (`http(s)://`, `www.`, or a bare-domain regex like `google.com`) -> `webbrowser.open()`; known folder aliases (`downloads`, `documents`, `desktop`, `pictures`) -> `os.startfile()`; known app aliases (`_APP_ALIASES` dict -- notepad, calc, explorer, chrome, cmd, powershell, vs code, etc.) -> `os.startfile()`; otherwise attempts `os.startfile(target)` as a best-effort raw guess, and if that raises `OSError`, gives an honest "I don't recognize X, try /fleet" reply rather than pretending to have done something. **Verified for real** -- "open notepad" actually launched Notepad.exe (confirmed via `tasklist`, real PID), not just a canned reply. Executes in under 0.3s, no LLM involved. Explicitly NOT solved: true anaphora ("open *that*" referring to something just discussed) needs conversational understanding the deterministic layer can't do -- only literal app/file/URL names work instantly; ambiguous/complex requests still need the explicit `/fleet` prefix to reach the real Claude Code CLI.

## Automatic fleet delegation (2026-08-01, session 4 continued)

Mike explicitly asked for the local-vs-fleet split to become automatic ("I won't speak [a prefix], but if something is very complicated, you allocate the task") -- rather than requiring an explicit `/fleet ` prefix. Added `_is_complex_request(text)` -- a deterministic keyword regex (`_FLEET_KEYWORDS`), NOT the local model judging its own delegation (that was tried before, see the "why the fleet delegation is a hardcoded prefix" section above, and it failed outright). Triggers on real-work verbs (build/deploy/debug/refactor/write code/research the/investigate), infra nouns (website/repo/database/supabase/stripe/shopify/vercel/api/server), file/folder language, and a hardcoded list of the agency's actual known project names (cloudskin, drip-store, mykonos, etc. -- a very strong, low-false-positive signal). Validated against 10 casual + 9 complex realistic example messages before deploying -- 19/19 correct after one fix (the first regex draft missed "research the top 5 competitors and summarize their pricing" because it required "research and/then summarize" adjacent; broadened to `research the|research \w+ (and|then)|...|competitors`).

**Wired into both surfaces:**
- `telegram_relay.py`: `is_auto_fleet = not is_explicit_fleet and _is_complex_request(text)` extends the existing `/fleet ` prefix check; auto-triggered messages send the same "this can take a few minutes" heads-up before running.
- `jarvis_voice.py` had **zero** fleet capability before this -- added `CLAUDE_EXE`, `FLEET_TIMEOUT_SECONDS`, `ask_fleet()` (mirrors telegram's, `subprocess.run([CLAUDE_EXE, "-p", task, "--output-format", "text"], timeout=1800)`), and wired it into `ask_hermes()`: on a complex-match, speaks an immediate spoken acknowledgment ("Got it, that needs real work -- let me get that handled...") via a new `_speak_full_text()` helper (same sentence-chunking as the streaming path, but for a complete non-streamed string) BEFORE running the slow blocking fleet call, then speaks the real result when it's done. This keeps the exchange feeling responsive even though the underlying fleet call can genuinely take minutes -- same pattern as a person saying "let me get that handled" before going quiet to actually do the work.

Smoke-tested the `ask_fleet()` subprocess plumbing itself with a trivial task (7.3s, correct output) -- did not run a real multi-minute complex task end-to-end in-session (too slow to wait on), so the *plumbing* is verified but a genuinely long real-world fleet delegation through voice hasn't been observed yet. Known real limitation, stated plainly to Mike: this is a keyword pre-filter, not true understanding -- it will have occasional misses (a complex request phrased without any trigger word) and rare false triggers (an innocuous sentence containing a trigger word) recognized as opportunities to keep tuning `_FLEET_KEYWORDS`, not as bugs to "fix" once and forget.

## Fleet permission-mode gap found and fixed, with a safety guardrail (2026-08-01, session 4 continued)

Ran a real end-to-end auto-fleet test ("check the cloudskin site and tell me if it's live") through jarvis_voice.py to validate the new auto-detection. Classifier and spoken-ack plumbing worked, but the actual `claude -p` fleet subprocess reported it **could not do anything** -- curl (Bash), PowerShell `Invoke-WebRequest`, `WebFetch`, and Vercel MCP tools were all refused with "requires approval". Root cause: `ask_fleet()` in both scripts had **no `--permission-mode` flag at all**, even though this project's own earlier memory documented the design as using `--permission-mode acceptEdits` and called it "confirmed working live" -- that flag had been dropped somewhere along the way (or the docs described intent that never fully landed in the code). Either way, this matters: `acceptEdits` alone would NOT have fixed this specific failure anyway, since the blocks were bash/web-fetch/MCP, not file edits.

**Decision (Mike explicitly chose after seeing the failure):** `--permission-mode bypassPermissions` -- full bypass, no approval prompts of any kind, in both `telegram_relay.py` and `jarvis_voice.py`'s `ask_fleet()`. Necessary because these run fully headless (voice/Telegram, no TTY, nobody present to click "approve") -- anything less than full bypass just reports "blocked" instead of doing the work, as directly demonstrated.

**Immediately after enabling this, Mike flagged the obvious follow-on risk: "make sure you don't affect the live site."** Real concern given cloudskin.com is a live e-commerce site with real Stripe payments -- bypassPermissions plus an imperfect keyword classifier (`_is_complex_request`, see above) means a misheard voice transcription or ambiguous phrasing could in principle trigger a real, unattended, unreviewed mutation. Mitigation added: `_AUTO_FLEET_SAFETY_PREAMBLE`, a fixed instruction block prepended to the task text **only for auto-detected requests** (not explicit `/fleet ` ones, where Mike consciously typed exactly what he wants) -- tells the fleet agent this is unattended with nobody reviewing actions, to default to inspect/check/report only, and to never deploy/push/modify production data/pricing/inventory/live-site content unless the request unambiguously and explicitly asked for that specific change. This is a prompt-level guardrail layered on top of the CLI-level bypass, not a replacement for it -- the fleet agent technically still CAN do anything, it's just told firmly to default to read-only when the request's intent is ambiguous.

**Verified for real, twice:** first run (no permission flag) correctly reported it was blocked and asked which tool to authorize, rather than guessing or hallucinating a fake answer -- itself a good sign of honest failure behavior. Second run (bypassPermissions + safety preamble, same exact task) actually executed real HTTP checks (confirmed `https://cloudskin.com` responds 200 in ~0.65s) and gave an accurate report of the site's real live state (deployed and healthy, but still behind the launch/password gate) -- stayed strictly read-only, respected an unauthorized Shopify connector rather than trying to force through it, took ~140s total for real verification work. No modification of any kind was attempted in either run.

**Open risk, stated plainly:** the safety preamble is a prompt instruction, not a hard technical constraint -- a sufficiently capable/determined agent or a sufficiently misleading transcription could still in principle cause it to act. This is a real, accepted trade-off for getting genuine unattended capability, not a solved problem. If a false-positive auto-fleet trigger on a genuinely destructive-sounding phrase becomes a real concern in practice, the next hardening step would be a narrower `--permission-mode acceptEdits`-plus-explicit-tool-allowlist rather than full `bypassPermissions`, at the cost of auto-fleet tasks needing explicit `/fleet` for anything beyond file edits.

## Full-system verification pass + one more real bug fixed (2026-08-01, session 4 end)

After all the above, ran a comprehensive functional pass across every feature (casual chat, remember, recall-in-conversation, explicit recall-list, deterministic open, fleet classifier, forget) through the live production code. Six of seven passed cleanly. Found: `_forget(needle)` used a strict substring check (`needle_lower in fact.lower()`), which fails on completely reasonable real phrasing -- "forget that my wifi password" against the stored fact "my office WiFi password is Sunset2026" doesn't match because "office" sits between "my" and "wifi" in the real fact, breaking contiguity. Fixed in both scripts: substring match first (exact phrase, preferred), falling back to a word-overlap check (>=60% of the needle's words present in the fact) when no exact substring exists. ## Pipelined TTS: killed the inter-sentence dead-air gap (2026-08-01, session 4 end)

## Watchdog races manual restarts -> TWO instances fight over the mic (2026-08-02)

`JarvisWatchdog` (native Windows scheduled task, every 5 min) restarts `jarvis_voice.py` whenever it finds none running. ## ROOT CAUSE of the PortAudioError: Windows mic master switch is OFF (2026-08-02)

The `sounddevice.PortAudioError: Unanticipated host error [PaErrorCode -9999] [MME error 1]` that blocked `jarvis_voice.py` from starting is **NOT** a driver quirk, not this hardware's known mic flakiness, and not caused by rapid Stop-Process kills (all of which were plausible-sounding guesses recorded earlier the same session -- they were wrong). Diagnosed properly by testing every device index and backend, then checking the OS consent store:

- `HKCU\...\CapabilityAccessManager\ConsentStore\microphone` = **Allow**
- `HKCU\...\ConsentStore\microphone\NonPackaged` = **Allow**
- `HKLM\...\CapabilityAccessManager\ConsentStore\microphone` = **Deny**  <- the machine-wide master switch, overrides both per-user Allows

Signature to recognize this instantly next time: the device still **enumerates fine** in `sd.query_devices()` and shows `Status: OK` in `Get-PnpDevice -Class AudioEndpoint`, but **every** index and **every** host API fails to open -- MME/DirectSound give `-9999 Unanticipated host error`, WASAPI gives `-9997 Invalid sample rate` at non-native rates and `-9996 Invalid device` at its native 48kHz. A genuine driver/device-in-use problem would not fail uniformly across all backends like that.

**Fix is a Windows privacy setting, not code:** Settings > Privacy & security > Microphone > turn ON "Microphone access" (the master toggle) and "Let desktop apps access your microphone". Left for Asteris to do himself -- flipping a machine-wide security/privacy setting is his call, not something to change silently on his behalf. Opened the page for him via `Start-Process 'ms-settings:privacy-microphone'`.

**RESOLVED same session:** Asteris flipped the toggle; HKLM value went `Deny` -> `Allow`, the mic then opened first try, and `jarvis_voice.py` started cleanly all the way to `Jarvis voice loop ready. / Listening for 'hey jarvis'...` with Kokoro TTS loaded. Confirmed stable afterward (same PIDs held across repeated checks, ~658MB RSS = models resident, matching the documented two-PID venv-trampoline non-bug). So the whole "mic is flaky on this Senary Audio hardware" theory from the earlier session should be treated with suspicion -- **check the HKLM consent value FIRST** before blaming hardware next time.

Traced it before assuming a real bug: one "duplicate" was `JarvisVaultWatch`'s own `--check-vault` CLI invocation happening to fire in the same window (its 30-min schedule landed right then) -- a real but harmless process that matches the same `-match 'telegram_relay\.py'` filter as the actual long-poll bot, since the filter doesn't distinguish CLI-flag runs from the persistent `main()` process. A second "duplicate" turned out to be the diagnostic PowerShell command *itself*, whose command-line text literally contains the string `telegram_relay.py` (because it's grepping for it), self-matching the same filter. **Lesson: when checking for duplicate instances of this script, exclude `--check-vault`/`--push-briefing` from the match and exclude the checking command's own PID, or you'll chase a false alarm.** The actual bot was never duplicated; there was exactly one real long-poll process the whole time, confirmed via its live established TCP connection to Telegram, not just process count.
2. **`JarvisVaultWatch` wouldn't actually have started its every-30-min cadence until 2026-08-04 00:00 -- a full day-plus late.** Root cause: its `CalendarTrigger`'s `Repetition` only becomes active FROM `StartBoundary` onward, and that was set to tomorrow midnight (a same-mistake-shape as `JarvisBriefing`'s dates, but those two both already lay in the past for today by the time this was built, so tomorrow was correctly their next real occurrence either way -- for the repeating task specifically, tomorrow midnight meant the *entire first day* of intended 30-min checks silently wouldn't happen). Fixed by re-registering with `StartBoundary` set to a few minutes after the fix (same day), confirmed via `Get-ScheduledTaskInfo`'s `NextRunTime` actually landing minutes out, not a day-plus out. **Lesson: for any `CalendarTrigger`+`Repetition` task meant to start "basically now," set `StartBoundary` to a few minutes in the future on TODAY'S date -- not midnight, not tomorrow -- and always confirm via `NextRunTime` after registering, since the XML registers successfully either way and gives no error for a "correct but not what you meant" start time.**

## Eleven features added in one pass: agency-facing Jarvis (2026-08-03)

Asteris asked for feature ideas, then said "do them all." Landed all eleven in `telegram_relay.py` (still the only surface -- voice is retired except for the NEW push-to-talk voice-note feature below, which is deliberately unrelated to the old always-listening loop). Every deterministic feature follows the file's established rule: no LLM touches factual data, only formats/reports it.

**1. Reminders** -- "remind me in 20 minutes to X" / "remind me at 3pm to X" / "remind me tomorrow at 9am to X" / "what are my reminders". Fully deterministic parsing (`_REMIND_IN_RE`/`_REMIND_AT_RE`), `reminders.json`. Ambiguous bare hours with no am/pm (e.g. "remind me at 3") resolve to whichever 12-hour reading is soonest in the real future -- verified against 7 phrasings including that exact ambiguous case. `JarvisReminders` (every 5 min, `--check-reminders`) fires anything due and re-queues on a failed send rather than dropping it.

**2. Push alerts on site status change** -- distinct from the pre-existing on-demand uptime check. `JarvisSiteWatch` (every 15 min, `--check-sites`) diffs each registry site's status against `site_status_state.json` and pushes ONLY on a real up/down transition (first-run guard, same shape as the vault watcher's). Verified live: baselined all 5 real sites as up, simulated a prior "down" state for CloudSkin, confirmed the alert fired and the state reconciled back to real "up".

**3. Morning agency digest** -- 07:30 only, via a NEW separate task `JarvisMorningDigest` (`--push-briefing --push-digest`), not a flag on the existing `JarvisBriefing`. The digest and plain-briefing cooldowns are tracked under separate keys in `briefing_state.json` (`last_digest_sent` vs `last_sent`) specifically so an unlock minutes before 07:30 can't silently eat that morning's digest. Addendum = fresh site check + vault additions in the last 24h (from a new `vault_additions_log.jsonl`, appended to inside `check_vault_and_report()`) + fleet calls in the last 24h (reusing `_load_jsonl_entries`/`_entries_within`, factored out of the pre-existing fleet-usage-query logic). Verified with real data: "Sites: all 5 up / Vault: no changes in the last 24h / Fleet: 0 call(s) in the last 24h" -- all three numbers independently cross-checked as correct.

**4. Telegram file-send (sendPhoto/sendDocument)** -- `requests` isn't installed for this interpreter, so this hand-rolls multipart/form-data with stdlib only (`_send_telegram_file`), matching the rest of the file's deliberate raw-urllib style. Verified for real against the actual Telegram API, not just "didn't throw": sent a real 1x1 PNG and a real .txt file, checked the JSON response's `"ok"` field directly (`True` both times).

**5. Client report on demand** -- "send cloudskin's report" / "report for drip barbershop" -- resolves the site against the registry, runs the EXISTING `generate_client_report.py` directly (no fleet, no LLM -- pure formatting of already-produced health-check history) and sends the HTML via the new file-send infra. Verified end-to-end for real: generated CloudSkin's actual report from its real health-check history and sent it.

**6. Fleet-shortcut mechanism** (`_handle_fleet_shortcut`) -- a shared dispatch for scoped, narrow, deliberately-read-only `/fleet` delegations triggered by a one-line message instead of a full session: "audit cloudskin" (condensed Hera-style score + top 3 issues), "pull assets from X" / "scrape X for a rebuild" (Hypnos-style intake, explicitly told not to build/deploy), "check for drift" / "any new deployments" (Vercel vs registry, see #9 below), "scan Business url.com" (see #8). All checked with HIGHER priority than the generic auto-fleet/big-build classifier, since these have their own already-safe prompts. Each is a REAL fleet call -- real token cost, unlike everything else in this list.

**7. Screenshot on demand** -- "screenshot cloudskin". Kept separate from the generic shortcut mechanism because it needs a post-fleet-call step the others don't: the fleet is told to save a PNG to a fixed path (`last_screenshot.png`), and the relay checks that file's mtime advanced past a captured `before_mtime` before sending it via `send_photo` -- so a fleet reply that *claims* success without actually producing a fresh file doesn't get treated as one.

**8. Prospect-scan from phone** -- "scan Acme Cafe acmecafe.gr" (also handles a comma and a bare or `https://` URL). Appends a real row to `prospecting-queue.md`'s existing Queue table (`_queue_prospect`, string-replace on the table's header marker) BEFORE dispatching a fleet prompt that replicates the real `prospect-scan` task's own house rule (never fabricate/exaggerate problems -- it damages Mike's reputation) for that one business, appends to `prospect-scan-results.md`, and moves the row to Scanned. If the queue write itself fails, the shortcut returns `(kind, error_message, None)` -- a `prompt=None` third element is a signal to the router "target IS the reply, don't call the fleet" -- so a local file-write failure can never trigger a real paid call. **Verified for real** (queue file actually got 3 test rows written during testing, confirmed the write mechanism works, then cleaned the test rows back out both times this happened -- test handlers with real side effects on shared files needs a cleanup step every time, not just a happy-path check).

**9. Weekly deployment-drift check** -- `JarvisDriftCheck` (Mondays 09:00, `--check-drift`), matching `nightly-site-health-check`'s own weekly cadence. **Real, open uncertainty, stated plainly**: whether a headless `claude -p` subprocess actually inherits this session's Vercel MCP connection, or whether that connector is session-scoped and invisible to a detached CLI call, was NOT verified (would need a real, several-minute, real-token fleet run to confirm either way). Hedged directly in the shared prompt (`_DRIFT_CHECK_PROMPT`, used by both the scheduled push and the on-demand "check for drift" shortcut): explicitly told to say plainly if the Vercel tools aren't reachable rather than confidently reporting "no drift" without ever having actually checked. If the weekly push ever comes back oddly silent/generic, check this first.

**10. Voice-note transcription** -- push-to-talk (Asteris explicitly sends a Telegram voice message), NOT a revival of the retired always-listening wake-word loop -- no wake word, no open mic, no self-echo risk, since Telegram itself delimits each note. Downloads via `getFile` + Telegram's file-serving URL, transcribes locally with faster-whisper. Required installing `faster-whisper` for system Python313 specifically (it wasn't there -- only the hermes-agent venv had it) via plain `pip install faster-whisper`; the actual `base` model weights were already cached at `~/.cache/huggingface/hub/models--Systran--faster-whisper-base` from the retired voice project (HuggingFace's cache is user-level, not venv-scoped), so no fresh download was needed -- confirmed by the model loading in 2.6s. **Verified for real with genuine speech**, not silence or noise: generated a real WAV via Windows' built-in `System.Speech` SAPI TTS (zero new install) saying "Remind me tomorrow at nine a m to call the client about the invoice", transcribed it correctly in 1.57s, including Whisper's own normalization of "nine a m" to "9am" -- which matters because that's exactly the format `_REMIND_AT_RE` expects, so a spoken reminder genuinely chains into the reminders feature above. The transcript is echoed back ("🎤 Heard: ...") before normal processing, so a bad transcription is visible rather than silently acted on. **Not verified**: the actual `getFile`-then-download step against a REAL Telegram-hosted voice file, since that only exists once a real voice message has actually been sent -- needs Asteris to try it live.

**11. Approval-in-chat for ambiguous auto-fleet actions** -- previously the auto-fleet safety preamble just silently defaulted to read-only whenever it found something beneficial-but-unrequested, with no way to say "actually yes, do that" short of retyping the whole request. `_AUTO_FLEET_SAFETY_PREAMBLE` now also teaches a fixed protocol: end the reply with exactly `PROPOSED_ACTION: <one sentence>` if there's a real but unrequested next step worth flagging. `_extract_and_strip_proposed_action()` scans any auto-fleet reply for that line, stores it in `pending_action.json` (one slot -- this is a 1:1 personal bot, not a queue) and replaces it with a plain "❓ Proposed: ... Reply yes to proceed, no to skip." A following bare yes/no (`_handle_pending_action_response`, checked with the HIGHEST priority of any handler, but only ever intercepts when a pending action genuinely exists -- confirmed normal chat like "hows it going" or a real question like "what time is it" both pass through completely untouched even WITH a pending action sitting there) resolves it: "yes" re-invokes `ask_fleet()` with the confirmed action (still the same bypassPermissions mechanism -- no new capability, just confirmed intent first) and re-runs the SAME proposed-action extraction on that result too, so a chain of confirmations is possible; "no" just clears it. Offline at confirm-time clears the pending action rather than trying to preserve it (consistent with how every other offline-fallback in this file already behaves) and tells Asteris to just re-ask if he still wants it. **Verified as a complete, real state machine** (not just individual pieces): no-pending-action passthrough, a simulated fleet reply's PROPOSED_ACTION line correctly extracted/stored/stripped, an unrelated message with a pending action correctly ignored, "yes" correctly resolving to a well-formed confirm prompt, and the pending action correctly cleared afterward -- six separate assertions, all correct. The actual re-invoked `ask_fleet()` call itself wasn't live-tested (real token cost for infrastructure that's already proven elsewhere in this file).

**A real, pre-existing bug found and fixed while building #5**: `_match_site_by_name` (factored out of the original `_handle_uptime_check`, now shared by uptime/report/shortcuts/screenshot) used to return on the FIRST site whose name shared any word with the query -- "DRIP Store" and "Drip Barbershop" both contain "drip", so "report for drip barbershop" silently resolved to "DRIP Store" instead, purely because it happens to sit first in the registry table. This means **the original uptime check had this exact bug live the whole time** ("is drip barbershop up" would have silently checked DRIP Store's URL instead), just never noticed because nobody had tried that specific phrasing before. Fixed to score every site by how many of ITS OWN name-words appear in the query and take the best match, not the first -- same fix shape as the earlier `_search_project_memory` match-count-over-recency correction. Verified both directions resolve correctly now, for both the report feature and the original uptime check.

**A real registration mistake worth knowing about**: re-saving one of these task XML files (via a Get-Content/Set-Content PowerShell round-trip with ambiguous default encoding) produced a DOUBLE-ENCODED file (extra null bytes between characters, confirmed by inspecting the raw bytes) that `schtasks` correctly rejected as malformed -- but a different one silently registered fine moments earlier with the exact same command shape, so this can look like flaky/random behavior if you don't check the actual bytes. Fix: use `[System.IO.File]::ReadAllText(path, [Text.Encoding]::UTF8)` / `WriteAllText(path, content, [Text.Encoding]::Unicode)` explicitly -- .NET's own encoding classes, not `Get-Content`/`Set-Content`'s default detection -- and spot-check the first few bytes (`FF FE 3C 00 3F 00 78 00...` = correct UTF-16LE `<?xml`) before trusting a registration succeeded.

Both times it was a false alarm -- either `JarvisSiteWatch`/`JarvisVaultWatch`'s own transient `--check-`-flag invocation happening to overlap the same process-list check, or the diagnostic PowerShell command's own command-line text self-matching the `telegram_relay.py` search pattern. When checking instance count, filter OUT anything with `--check-`/`--push-` in its command line and anchor the pattern to end right after `telegram_relay.py` (`'telegram_relay\.py"?\s*$'`) so a CLI-mode run or the checking command itself can't masquerade as a second bot.
