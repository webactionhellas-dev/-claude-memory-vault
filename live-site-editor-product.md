Think big ("crazy, crazy"). This is a differentiator + revenue driver, not a feature for one site.

**Why it is very buildable (the house architecture is already ~80% there):**
- House sites already tag editable elements with `data-content` / `data-content-img` / `data-content-link` attributes, and `content.js` reads them and applies owner overrides from the Supabase `cloudskin_content` table (key/value). The `/studio` panel already writes those keys via the `studio_save` RPC (password via `studio_auth`, bcrypt in `studio_secret`, deny-all RLS).
- So an in-place editor is a NEW UI over the SAME data layer: an "edit mode" overlay that (a) finds `data-content*` elements, (b) makes them click-to-edit on the page (contentEditable for text, an image picker → Storage for images, a friendly dropdown for link targets, toggles for show/order), (c) saves through the same `studio_save`/Storage path, (d) live-updates the DOM. The plumbing (attributes + content table + save + Storage uploads + snapshot bake) already exists on CloudSkin.

**Proposed phased plan (Boss, for Mike to approve/scope):**
1. **Spike on CloudSkin** — evolve the existing Studio into an on-page editor: an "Edit this page" toggle (owner-gated) that turns `data-content*` elements into inline editors on the real site; prove text + image + link + show/hide/order end-to-end. Low risk (reuses the live data layer), high signal.
2. **Generalize into a house package** — extract a drop-in `live-editor.js` + a small convention (`data-edit="text|image|link|list|section"`) + a generic `site_content` table + save RPC + RLS + Storage bucket. One include gives ANY house site (marketing-starter, commerce-starter) the editor. This is the reusable product core.
3. **Productize (the sellable layer)** — owner auth + roles, draft vs publish, undo/history, a media library, per-client editor theming, onboarding, and (if we go SaaS) multi-tenant. This is what makes it a saleable capability / retainer hook ("every site we build edits itself; you never touch a dashboard").
